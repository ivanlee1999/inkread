# Saved library storage contract

The library is device-local and independent of RSS accounts. `SavedLibrary` is a new Room database at version 1. It does not alter Reader DB7, article rows, account deletion, cache-clearing, feed subscriptions, or RSS read state. The provider interface only declares possible future capabilities; there are no provider credentials, external service integrations, or synchronization.

## Durable text and bounded images

Bodies live in `filesDir/saved-library/<item UUID>/<file revision UUID>/content.html`; downloaded images use opaque immutable filenames beside them. This is not cache storage. Files are written and fsynced in a temporary revision directory, atomically renamed, then referenced by an update-only metadata transaction. Failed writes leave the old revision readable. List queries contain metadata only, never HTML.

Text and inline-image completeness are distinct. Content `READY` means durable captured text. An RSS snapshot can be a summary; this status does not assert that the entire publisher article was extracted. Image `NONE` means no inline image candidates, `READY` means all counted inline images retained, `PARTIAL` means some, and `FAILED` means none were retained. `PENDING` means queued/in progress. These statuses do not promise offline video, audio, stylesheets, or arbitrary embedded media. Embedded data images and unsupported image formats are explicitly counted missing rather than silently treated as complete. They are not sent to a network downloader.

Bounds are 2 MiB per page/text body, 12 unique images per article, 2 MiB per image, 12 MiB retained images per article, and 256 MiB total managed files. The total includes text, retained images, and staged immutable revisions. Existing text and images are never silently evicted to admit another item. New images that do not fit are declined with a visible partial/failure reason. A new text save that cannot fit fails visibly. Removal is explicit.

## Revisions and reading position

`contentRevision` is the opaque logical text revision used for reading-anchor compare-and-set. `fileRevision` is the immutable on-disk version and can change when missing images arrive without changing text. Image-only updates preserve logical revision, anchor, existing image paths, and element ordering. An old anchor cannot update a different text revision. Anchor-only metadata writes do not emit duplicate `SavedItem` values. Obsolete HTML files can be pruned because readers already hold HTML strings; retained image files remain valid for an open reader.

## Queue and crash recovery

The capture transaction assigns a random download token. WorkManager work is unique per item/token generation and carries a per-item tag for cancellation. Generation-specific uniqueness matters: a pre-crash older job must not suppress a newer token with `KEEP`. Re-observing the library or an item in a new repository instance reconciles persisted pending tokens off the main thread without reading article bodies. WorkManager also persists already-enqueued work across process death.

At most two articles download concurrently. The existing public-article client supplies the ordinary bounded fetch, DNS/redirect policy and eight-second call cap; normal readability extraction is reused. Each job examines no more than 12 image downloads. There is no unbounded automatic network retry loop. Failures are durable and explicitly retryable. Network constraints leave work queued until connected.

Workers compare the item ID and generation token before every publication. Deletion first removes the metadata row, cancels tagged work, and removes files. A late result cannot insert or recreate the row. Retry supersedes the token. An interrupted worker can resume the same pending generation; a fresh observation repairs the Room-to-enqueue crash gap.

## Verification limits

Synthetic standalone JVM tests exercise file durability, quotas, deduplication, ordinary image rewriting, repository concurrency, cancellation, retry and delete races. They perform no real article requests. They do not establish Android lifecycle/WorkManager execution, Room-generated code correctness, device rendering, or an end-to-end APK pass. The exported Room v1 identity bundle was generated by the authorized Android/KSP build at commit 2b5df3b (Actions run 39813921459), not hand-invented. That initial run stopped at an unrelated Kotlin gesture-callback type error before native tests; exporting the schema is not evidence of a complete Android pass.
